# 2026-07-15 第一次客户沟通总结

原始记录：`customer-communications/raw/0715_yipei.txt`

## 一句话结论

客户想要的不是单纯“提高科研材料撰写效率”的工具，而是一个面向专科院校教师的科研立项引导助手。它需要通过有规则的对话，帮助老师想清楚研究问题、研究方法、成果形式，并最终生成符合学校格式要求的课题申报书。

## 客户核心诉求

1. 帮助老师把课题想清楚，而不是只替老师写材料。
2. 引导老师回答关键问题：解决什么问题、用什么方法解决、产出什么成果。
3. 让成果不止于论文，还要包含可复用、工具性、流程性或实践改进类成果。
4. 通过聊天式流程降低老师使用 AI 和申报课题的门槛。
5. 将老师的朴素表达转化为结构化、符合申报要求的材料。
6. 在知识库、流程和体验上形成比通用大模型更贴近学校场景的封装。

## 明确场景

### 场景一：小白老师不知道申报什么课题

老师可能没有明确课题方向。助手需要从老师的岗位、教学工作、管理工作、痛点、学校要求和政策方向出发，帮助老师发现可申报课题。

典型路径：

```text
了解教师背景
-> 挖掘教学或工作问题
-> 结合学校要求和申报指南
-> 推荐几个课题方向
-> 选择方向
-> 继续澄清研究问题、方法和成果
-> 生成申报书初稿
```

### 场景二：已有科研基础的老师申报更高层级课题

老师已经做过课题或有成果，希望结合过往材料、政策文件、申报指南和当前研究热点，申报更高水平课题。

典型路径：

```text
上传过往课题和成果
-> 上传申报指南或政策文件
-> 分析已有成果基础
-> 推荐升级方向
-> 设计更高层级课题
-> 生成申报书材料
```

## 第一版建议聚焦

第一版 demo 建议只聚焦“场景一：小白老师不知道申报什么课题”。原因：

1. 这是客户表达最清楚、最有差异化价值的场景。
2. 它最能体现“引导老师思考”，而不是“AI 代写”。
3. 对资料依赖较少，适合先做流程验证。
4. 下次客户沟通可以用它校准提问顺序、质量标准和最终产出。

## 会议遗留事项

### 我方待办

1. 将产品定位从“科研提效工具”调整为“科研立项引导助手”。
2. 设计小白老师立项申请的用户流程。
3. 准备一个可演示的对话 demo。
4. 梳理申报书质量判断标准。
5. 列出需要客户提供的资料清单。

### 客户侧支持

1. 提供优秀课题申报书样例。
2. 提供学校申报书模板和格式要求。
3. 提供课题申报指南、政策文件或征集通知。
4. 协助访谈科研处、教务处或优秀申报教师。
5. 补充客户自己对“好申报书”的判断标准。

## 后续推进建议

下一次客户沟通不应以“完整产品演示”为目标，而应以“流程校准”为目标。建议围绕三个问题让客户确认：

1. 老师进入系统后的提问顺序是否合理？
2. 系统对“好课题/好成果”的判断是否符合学校要求？
3. 最终生成的申报书结构是否贴近学校模板？
