# 科研教练交互简化设计

## 目标

在保留证据边界、阶段门槛、教师确认和长期记忆安全规则的前提下，把 `research-proposal-coach` 从“内部状态驱动的流程问答”调整为“老师能理解当前目的、能表达自己的判断、再由系统生成阶段材料”的教练式对话。

本次修改针对已观察到的六类问题：首次建档过重、内部术语外露、确认节点碎片化、方向选择缺少理由、研究产物先于整体骨架、学习反馈与记忆更新没有形成闭环。

## 方案比较

### 方案 A：仅修改措辞

只把 A/B/C、研究术语和状态名称换成通俗中文。

- 优点：修改小、风险低。
- 缺点：不能解决入口过重、产物跳步、无意义重复确认和记忆闭环缺失。

### 方案 B：保留后台状态，重构前台交互（采用）

保留现有 10 个内部状态、证据来源、质量分级和 Material Passport；增加教师可见的简化规则、研究骨架卡和交互评测。内部状态不直接决定回复格式，而是转译成自然语言和少量关键决策。

- 优点：不破坏现有检索、画像和质量体系，直接解决本次真实会话暴露的问题。
- 缺点：需要同时调整入口、引导、阶段契约、模块和评测。

### 方案 C：重写为四阶段状态机

删除现有 8 阶段/10 状态设计，重写为“问题—方向—方案—产物”四阶段。

- 优点：前台和后台都更简单。
- 缺点：会破坏已实现的画像、证据、申报映射和质量检查契约，超出本次交互优化范围。

## 设计原则

1. **后台严格，前台轻量。** 内部继续维护状态、来源和质量等级，但教师默认只看到自然语言结果。
2. **先说明为什么，再生成什么。** 每个大型产物生成前说明当前阶段、产物用途和待确认事项。
3. **确认的是研究判断，不是系统术语。** 将多个低风险事实合并确认，只在方向、核心问题、研究骨架、证据边界和申报映射处停顿。
4. **老师先表达，系统再挑战。** 关键节点要求老师给出一个短理由或修订，而不只接受系统选项。
5. **推断不能冒充确认。** 用户改变方向但没有说明原因时，原因保持未知或标为系统推测，不写成 `user_confirmed`。
6. **记忆必须产生可见收益。** 画像冲突、目标变化和交互偏好在里程碑处集中复核，不在每轮打断对话。

## 交互设计

### 1. 渐进式入口

首次使用且本机没有档案时，只问一个路由问题：

> 可以先临时聊，方向清楚后再决定是否保存；也可以现在建立教师档案。你想先临时聊，还是现在建档？

- 推荐“先临时聊”，因为它能最快进入真实问题，同时不写入长期档案。
- 用户选择现在建档时，一次性收集最小字段并给出一张紧凑摘要，不再连续使用多个选项弹窗。
- 返回用户仍只问一次身份确认，确认后再读取历史。
- 用户选择临时会话后立即进入普通辅导；会话结束最多邀请归档一次。

### 2. 教师可见的阶段说明

每次进入新阶段或准备生成大型产物时，使用三句话以内的“阶段说明”：

- 现在在解决什么问题；
- 为什么此时需要这一步；
- 老师当前只需要决定什么。

不向教师默认展示 `teacher_profile`、`FULL`、`MANDATORY`、A/B/C 或 `user_confirmed` 等内部代码。教师可见状态统一为：

- 已确认；
- 系统建议，待你判断；
- 有检索或材料依据；
- 还缺材料；
- 目前只能形成阶段方案；
- 当前条件可形成申报结构稿。

内部代码继续写入 Passport 和维护日志，管理员明确要求时才显示。

### 3. 方向比较使用真实场景

方向建议先使用课堂或工作画面，再在括号中补充研究名称。每个方向只展示：

- 课堂/工作中具体改变什么；
- 学生或工作对象要做什么；
- 可以收集什么证据；
- 实施成本和主要风险。

老师选择方向时，增加一个低负担问题：“你更看重它解决的问题，还是它比较容易实施？”老师可用一句话回答，也可跳过；跳过不会阻塞，但系统不得替老师编造理由。

### 4. 研究骨架卡

在生成题库、量表、任务单、长篇综述或申报段落前，先展示一张研究骨架卡：

| 字段 | 内容 |
|---|---|
| 真实问题 | 谁在什么场景中出现了什么可观察问题 |
| 核心问题 | 研究准备回答什么 |
| 改变措施 | 教师准备改变什么教学或工作做法 |
| 判断证据 | 收集什么数据、如何判断变化 |
| 预期成果 | 论文之外形成什么可复用产物 |
| 结论边界 | 当前样本和材料允许说明到什么程度 |

老师可以一次确认整张卡，也可以只修改其中一项。卡片未确认时可以继续讨论或提供小样，但不得直接生成会被误认为已定稿的大型产物。

### 5. 目标变化路由

当老师从“找方向”切换为“论文”“课题申报”或“只解决教学问题”时，只做一次简短确认，并更新当前目标：

- 论文：强调可回答问题、数据设计、文献与论文结构；
- 课题申报：强调指南、模板、方法成果和学校适配；
- 教学改进：可以停在实践方案，不强迫进入申报材料。

共享的上游信息继续复用，但不得把不同目标的最终产物混为一谈。

### 6. 学习反馈与记忆闭环

学习反馈不再机械地出现在每个模块末尾，只在以下里程碑出现：确认方向、确认研究骨架、完成文献理解、结束会话。格式限定为三项：

- 你已经想清楚的一个点；
- 当前最需要补强的一个点；
- 下一步最值得收集或阅读的材料。

画像、目标、研究方向或偏好发生变化时，先用于当前会话；在里程碑或会话结束时集中列出待更新条目，逐条请求保存确认。未确认的推断不得写入长期记忆。

## 内部状态与用户体验的边界

现有 10 个内部状态继续保留，避免破坏质量控制。用户可见流程压缩为四个自然阶段：

1. 找到真实问题；
2. 比较并选择研究方向；
3. 确认研究骨架和证据；
4. 生成阶段产物或申报结构稿。

多个内部状态可以在一次自然对话中推进。只有会改变研究方向、方法或最终产物的决策才必须显式确认；课程名称、人数等低风险事实可以在总结中合并确认。

## 异常与降级

- 如果交互组件的“其他”选项没有返回自定义文字，立即改为一个自由文本问题，不重复整套表单。
- 如果老师连续两次只回答“好的/都行”，将对话健康标为黄色，停止继续生成大型产物，改问一个具体例子或请老师修改研究骨架卡中的一项。
- 如果老师要求直接生成，允许快速模式，但仍须先展示研究骨架卡；老师可以一次确认整卡，不必逐字段确认。
- 如果用户目标变化但拒绝澄清，继续提供共同上游工作，并把最终产物类型标为未确定。

## 测试策略

先增加失败测试，再修改 Skill：

1. 首次模糊请求只触发一个路由问题，不直接索取五项资料。
2. 教师可见回复不得默认暴露 A/B/C、FULL、MANDATORY 等内部代码。
3. 方向选项必须包含具体场景，并允许记录“原因未知”。
4. 大型产物前必须先展示并确认研究骨架卡。
5. 目标从课题申报切换到论文时必须重新确认当前目标。
6. 学习反馈必须在里程碑出现，且限制为三项。
7. 未确认的方向切换原因不得保存为 `user_confirmed`。
8. 现有画像、临时会话、文献检索和证据追踪测试必须继续通过。

修改完成后运行全部 Node 测试、Skill 快速校验、源目录与安装副本一致性检查，并重新打包 `skills/research-proposal-coach.zip`。

## 成功标准

- 新用户可以在一次低负担选择后进入真实问题讨论。
- 教师不需要理解内部状态和质量代码。
- 每个大型产物都能回答“为什么现在做、它在研究中起什么作用”。
- 关键方向至少包含一次教师自己的判断或明确标记“原因未知”。
- 研究骨架未确认时不会直接越级生成大型产物。
- 会话结束能给出可见的学习反馈和待保存变化，而不是只有后台记录。
- 现有安全、来源、画像和文献完整性约束不退化。
