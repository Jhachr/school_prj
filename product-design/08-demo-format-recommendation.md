# Demo 展示形式建议

## 结论

当前静态对话脚本适合内部排练，但不适合作为客户主要演示形式。客户更容易理解的形式是：

```text
演示页面/文档 + 受控对话 + 实时产物面板
```

也就是说，现场不要只读聊天记录，而要让客户同时看到：

1. 当前处在哪个阶段
2. 系统为什么追问
3. 哪些信息已经确认
4. 哪些信息是 `user_confirmed`、`ai_suggestion`、`material_verified`、`demo_fixture` 或 `missing`
5. 最终材料如何被填入申报书字段

## 推荐方案

### 方案 A：受控对话原型

形式：

```text
左侧：老师与助手对话
右侧：阶段状态、已确认字段、缺失字段、生成产物
```

优点：

- 最能体现“科研教练”价值。
- 客户能看到系统不是随便聊天，而是按规则推进。
- 后续容易过渡到真实 Agent/Skill。

缺点：

- 需要准备一个可运行或半自动的演示界面。

建议：作为第一次客户演示的主方案。

### 方案 B：Markdown 受控演示

形式：

```text
用 Markdown 文档分段展示：
输入 -> 系统判断 -> 追问 -> 用户回答 -> 阶段产物
```

优点：

- 准备成本低。
- 稳定，不怕现场系统出错。
- 适合早期流程校准。

缺点：

- 交互感弱。
- 客户可能感知为静态方案。

建议：作为兜底方案。

### 方案 C：PPT/HTML 演示稿

形式：

```text
先讲业务拆解，再展示 demo 截图或流程动画，最后展示产物样例。
```

优点：

- 适合对齐领导和非技术角色。
- 便于讲清楚边界、价值和下一步。

缺点：

- 不足以证明系统能“追问和纠偏”。

建议：作为会议开场和总结材料，不作为唯一 demo。

## 第一次演示推荐组合

```text
1. 5 分钟 PPT/Markdown：复述需求、说明首版边界
2. 10 分钟受控对话：从“AI+教育”开始纠偏
3. 5 分钟产物展示：课题方案卡 + 文献综述草稿 + 字段映射稿 + 待补充清单 + 质量结果
4. 10 分钟客户确认：提问顺序、输出结构、质量规则
```

## 最小可运行 demo 的建议形态

第一版不必做完整前端，可以用一个轻量受控原型：

```text
左侧：模拟老师与助手对话、上一步/下一步/重置
右侧：阶段状态、已确认字段、缺失字段、最终产物
来源：user_confirmed / ai_suggestion / material_verified / demo_fixture / missing
输出：课题方案卡、文献综述草稿、申报书字段映射稿、待补充清单、质量结果
```

这个形式比纯聊天更适合客户，因为它能把产品的专业性显性化：客户看到的不只是“AI 会说话”，而是一套可管理、可审查、可沉淀的科研申报流程。

当前仓库中的实现位于 `demo/`。该网页只用于第一次流程验证，正式版本将在成熟 Harness 中运行科研立项 Skill。
