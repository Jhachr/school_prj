# 立项引导阶段规则状态表

## 用途

本文档把用户流程从"业务描述"转化为可执行的产品规则。每个阶段定义:必须收集的输入字段、阻断式通过条件、追问与异常处理策略、结构化输出字段、确认状态标记。

该状态表兼容 Skill、Agent、普通应用三种实现方式:Skill 可按阶段拆分为子流程,Agent 可按通过条件做路由判断,普通应用可按字段做表单校验。

配套文档:`01-novice-teacher-user-flow.md`(业务流程描述)、`03-proposal-quality-rubric.md`(质量分级)。

## 状态标记规则

### 字段确认状态

每条收集到的信息必须标记来源,区分用户确认与 AI 推测:

| 标记 | 含义 | 处理方式 |
|---|---|---|
| `已确认` | 用户在对话中明确认可 | 可直接进入申报书初稿 |
| `AI推测` | 助手基于对话推断,未经用户确认 | 生成时标注,进入下一阶段前必须请用户确认 |
| `待补充` | 信息缺失,尚未获取 | 阻断申报书完整生成,在产出物中标记 |

### 阶段状态

| 状态 | 含义 |
|---|---|
| `未进入` | 流程尚未到达 |
| `进行中` | 正在收集信息或追问 |
| `已通过` | 满足通过条件,可进入下一阶段 |
| `已阻断` | 关键字段缺失,不可进入下一阶段 |
| `已回退` | 用户中途改方向,回到指定阶段重做 |

## 各阶段详细规则

### 阶段 1:入口说明

- **目标**:让老师理解这是引导工具,不是代写工具。
- **输入字段**:无。
- **通过条件**:用户回应表示理解并愿意开始。
- **追问策略**:若用户直接要求"帮我写一份申报书",不直接拒绝,而是说明"我会一步步引导您想清楚,最后再整理成申报书结构"。
- **输出字段**:`session_start = true`。
- **确认状态**:无需确认。

### 阶段 2:教师画像采集

- **目标**:了解老师身份、工作场景、可转化为课题的资源。
- **必须收集字段**:
  - `dept`:所属院系或部门
  - `role`:岗位角色
  - `courses`:教授课程或负责工作
  - `recent_work`:近两年重点工作
  - `research_exp`:过往科研或项目经验
  - `school_req`:学校或部门对其工作的要求
- **阻断式通过条件**:至少获得 `dept` + `role` + `courses` 三项;否则不进入工作问题挖掘。
- **追问策略**:
  - 回答只有职称和姓名 → 追问"您平时主要教哪门课,或负责哪块工作?"
  - 没有教学或管理场景 → 追问"最近一周您花时间最多的事情是什么?"
  - 拒绝回答 → 降低压力,改问一个具体问题:"您最近一次比较头疼的教学或工作情况是什么?"
  - 中途改方向 → 记录原画像,询问"您是想补充背景,还是想换一个方向重新开始?"
- **输出字段**:`teacher_profile` 结构体,各字段标记确认状态。
- **确认状态**:用户原话标 `已确认`,助手归纳的总结标 `AI推测` 并请用户确认。

### 阶段 3:工作问题挖掘

- **目标**:从日常工作中提取真实、具体、可研究的问题。这是纠偏收敛的第一道关卡。
- **必须收集字段**:
  - `pain_point`:真实痛点
  - `scenario`:发生场景(课程/环节/学生群体)
  - `target_object`:问题对象
  - `cause_hint`:初步原因或反复出现的证据
- **阻断式通过条件**:问题来自真实场景,且能落到对象+情境;若问题过大(如"提升教学质量")必须先细化。
- **追问策略(纠偏收敛核心)**:
  - 用户输入空泛方向如"我想做 AI+教育" → 不直接生成课题,追问:"具体是哪门课、哪个学生群体、哪个教学环节?"
  - 问题过大如"提升教学质量" → 持续追问:"这个质量具体指什么?在哪个环节最明显?"
  - 问题只有口号没有场景 → 追问:"最近一次遇到这个问题是什么时候,具体情况是?"
  - 拒绝回答 → 提供选项式引导:"您觉得以下哪个更接近:A 任务太抽象 B 难度不合适 C 评价不清晰 D 组织方式问题"
  - 中途改方向 → 记录原问题,确认是否放弃当前问题挖掘
- **输出字段**:`problem_brief`,包含上述字段及确认状态。
- **确认状态**:场景和对象由用户原话确认;原因若为助手推断标 `AI推测`。

### 阶段 4:课题方向推荐

- **目标**:基于画像与问题,给出 2-3 个可申报方向。
- **必须收集字段(前置)**:`teacher_profile` 和 `problem_brief` 均已通过。
- **阻断式通过条件**:阶段 2、3 已通过;否则回退。
- **每个方向输出字段**:
  - `title`:暂定课题名称
  - `linked_problem`:对应真实问题
  - `object`:研究对象
  - `method_hint`:可能的方法
  - `outcome_hint`:预期成果
  - `reason`:适合申报的理由
  - `risk`:主要风险
- **追问策略**:
  - 用户全部不选 → 追问"这几个方向里,哪个和您的工作最接近?"或调整方向重新推荐
  - 用户想自己提方向 → 接受,但需走阶段 3 的细化检查
- **输出字段**:`direction_options[]`。
- **确认状态**:方向内容为 `AI推测`,需在阶段 5 由用户确认。

### 阶段 5:方向确认

- **目标**:让老师明确选定一个方向,并确认资源条件。
- **必须收集字段**:
  - `selected_direction`:用户选择
  - `selection_reason`:选择理由
  - `resource_available`:是否有条件开展(数据/案例/试点场地)
  - `school_acceptance`:学校或部门是否可能认可
- **阻断式通过条件**:用户明确选定一个方向;资源条件基本可行。
- **追问策略**:
  - 只说"听起来可以" → 追问"这个方向和您的工作具体怎么关联?"
  - 资源不足 → 提示降低范围或调整研究对象
  - 拒绝确认 → 不进入研究问题澄清,停留在本阶段
- **输出字段**:`confirmed_direction`。
- **确认状态**:必须人工确认,标记为 `已确认` 后方可进入阶段 6。

### 阶段 6:研究问题澄清

- **目标**:把方向变成可研究的问题。
- **必须收集字段**:
  - `core_question`:核心研究问题(一句话)
  - `object`:研究对象
  - `scenario`:研究场景
  - `current_pain`:当前痛点
  - `improvement_goal`:改进目标
  - `evaluation`:评价方式
- **阻断式通过条件**:核心研究问题可用一句话表述,且包含对象+场景+改进目标。
- **追问策略**:
  - 只有课题名称没有研究问题 → "你想验证、改进或形成什么结论?"
  - 目标不可测 → "具体提升什么?如何观察或评价?"
  - 中途改方向 → 回退到阶段 4 或 5
- **输出字段**:`research_question` 结构体。
- **确认状态**:必须人工确认,核心问题经用户认可后标记 `已确认`。

### 阶段 7:文献与政策支撑

- **目标**:帮助老师理解已有研究、政策方向和申报依据。首版用演示数据模拟,不接真实检索。
- **必须收集字段**:
  - `research_status`:研究现状概括
  - `research_gap`:已有研究不足
  - `policy_link`:政策或学校要求关联
  - `entry_point`:本课题切入点
- **阻断式通过条件**:至少说明政策/申报导向与本课题的关系。
- **追问策略**:
  - 无真实材料 → 使用演示数据,明确标注【演示数据】,禁止伪造引用
  - 政策只是贴标签 → "哪条政策和你的课题直接相关?它要求什么?"
  - 用户能提供材料 → 引用并标注来源
- **输出字段**:`literature_policy_summary`,标注每条依据是真实材料还是演示数据。
- **确认状态**:演示数据标 `AI推测` 并注明;真实材料标 `已确认` 并注明来源。

### 阶段 8:方法路径设计

- **目标**:把想法变成可执行的研究方案。
- **必须收集字段**:
  - `method_type`:方法类型(问卷/访谈/观察/行动研究/案例/实验等)
  - `data_source`:数据来源
  - `steps`:实施步骤
  - `feasibility`:周期、资源、对象是否现实
- **阻断式通过条件**:方法与问题匹配,且数据来源现实可获得。
- **追问策略**:
  - 方法堆砌无法执行 → "你准备从哪里获得数据或案例?"
  - 周期不符 → "这个方法在课题周期内能完成吗?如果不能,可以简化哪一步?"
  - 拒绝回答方法 → 提供与方法库匹配的选项
- **输出字段**:`method_plan`。
- **确认状态**:必须人工确认。

### 阶段 9:成果形式设计

- **目标**:避免成果只有论文,满足工具性、流程性、可复用性。
- **必须收集字段**:
  - `outcomes[]`:成果清单
  - `reusability`:可复用性说明
  - `non_paper`:是否至少一个非论文成果
- **阻断式通过条件**:至少包含一个非论文可复用成果。
- **追问策略**:
  - 只有论文 → "其他老师能复用什么工具、流程或资源?"
  - 成果不具体 → "这个成果具体是什么形式?谁会用?"
- **输出字段**:`outcome_list`。
- **确认状态**:必须人工确认。

### 阶段 10:申报书初稿生成

- **目标**:基于阶段 5-9 已确认信息,生成申报书初稿。
- **前置条件**:阶段 5、6、8、9 均已通过(阶段 7 至少演示数据已就绪)。
- **阻断式通过条件**:无硬性门槛字段缺失(见 `03-proposal-quality-rubric.md` 硬性门槛清单)。
- **追问策略**:
  - 存在硬性缺失 → 不生成完整初稿,返回对应阶段追问
  - 存在可补充项缺失 → 生成初稿但标注风险与待补充项
- **输出字段**:`proposal_draft`,每个栏目标记确认状态与来源。
- **确认状态**:必须人工确认。

### 阶段 11:质量检查与追问

- **目标**:按十维检查表评估初稿,针对薄弱部分追问。
- **输入字段**:十维检查结果。
- **阻断式通过条件**:达到 A 级(见 `03-proposal-quality-rubric.md`)。
- **追问策略**:
  - B 级 → 生成方案摘要,继续追问薄弱环节
  - C 级 → 回退到工作问题挖掘或方向确认阶段
- **输出字段**:`quality_report`,含等级、扣分项、追问建议。
- **确认状态**:等级判断为系统自动,无需人工确认;但追问结果需用户确认。

### 阶段 12:定稿导出

- **目标**:输出老师可继续修改或提交的材料。
- **前置条件**:质量等级为 A,或客户明确接受当前风险。
- **输出字段**:
  - 课题方案卡(见 `06-deliverable-templates.md`)
  - 申报书字段映射稿(见 `06-deliverable-templates.md`)
- **确认状态**:必须人工确认定稿。

## 异常处理通用策略

| 异常场景 | 处理策略 |
|---|---|
| 用户回答模糊 | 不接受模糊回答作为已确认;追问至具体场景或用选项式引导 |
| 用户拒绝回答 | 降低问题颗粒度,提供选项;连续拒绝 2 次则标记待补充,不强行阻断 |
| 用户中途改方向 | 记录已收集信息,询问回退到哪个阶段;不静默丢弃已有内容 |
| 用户要求直接代写 | 说明产品定位为引导,不直接代写;若坚持,可在定稿阶段提供初稿由用户修改 |
| 信息仅为 AI 推测 | 必须在进入下一阶段前请用户确认;未确认的推测不进入申报书已确认内容 |
| 演示数据被误当真实 | 所有演示数据必须标注【演示数据】,禁止对外声称是真实检索结果 |

## 纠偏收敛规则(核心差异化)

纠偏收敛是区别于普通聊天机器人的核心能力,贯穿阶段 3-6:

1. **识别空泛**:用户输入如"我想做 AI+教育""提升教学质量",系统识别为空泛,不直接生成课题。
2. **持续追问**:围绕具体课程、学生群体、教学环节、可获取数据持续追问。
3. **收敛验证**:收敛后验证是否落到对象+场景+改进目标,未达标继续追问。
4. **阻断生成**:研究问题未收敛为可落地表述时,阻断进入方法路径设计。

> 该规则在 Demo 中必须完整演示一次纠偏过程(见 `02-demo-conversation-script.md` 纠偏演示片段)。
