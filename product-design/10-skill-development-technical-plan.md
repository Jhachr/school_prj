## 0820 沟通后的核心判断

客户已经认可立项申请是首版最重要场景，也认可从教师画像、选题、文献综述、研究问题、方法成果到申报材料的主流程。需要调整的是产品重心：正式 Skill 不能只是把 8 个阶段串起来并替老师生成材料，而要像科研导师或学伴一样，在每个关键模块中引导老师思考、解释判断依据、追问薄弱环节，并让老师在完成申报书的过程中提升科研理解。

因此，后续开发应从“线性流程编排”升级为“模块化引导循环”：

```text
用户初始输入
-> Skill 生成结构化草稿
-> Skill 解释判断原则
-> Skill 追问关键问题
-> 用户补充或确认
-> Skill 修订草稿
-> Skill 记录短板和学习建议
-> 进入下一模块或回退修正
```

最低可接受的 1.0 是：老师给出有限输入后，系统按内置规则生成阶段性材料，并至少追问一轮以降低“垃圾进、垃圾出”的风险。

理想 2.0 是：系统在每个模块里显式承担教练职责，引导老师理解什么是好问题、好方法、好成果、好创新点，并沉淀老师的长短板和后续阅读建议。

长期方向是：围绕日志、评测和人工维护建立优化 loop。现阶段不承诺全自动自学习，但必须从第一版开始记录足够的过程数据，让后续人工评测和规则迭代有依据。

## 目标与边界

### 首版目标

首版 Skill 聚焦“专科院校小白老师不知道申报什么课题”的立项申请场景，帮助老师完成：

1. 明确教师画像和真实工作场景。
2. 从空泛意图中挖掘可研究问题。
3. 形成 2-3 个可比较课题方向并确认一个方向。
4. 生成并修订文献综述草稿。
5. 明确研究问题、方法路径、创新点和成果清单。
6. 映射到学校申报书字段，输出结构化材料草稿。
7. 输出质量等级、缺口清单、老师短板和学习建议。

### 首版不做

1. 不做完整科研生命周期，不覆盖结题、论文投稿、成果管理。
2. 不承诺自动连接学校人事、科研、教学系统；教师画像可先由用户输入或客户提供材料导入。
3. 不承诺全自动自学习，只保留日志和评测数据，为人工迭代准备。
4. 不把系统产物表述为“可直接提交的正式申报书”。
5. 不把没有真实检索结果的文献综述当作真实依据。

## 交付形态

交付物应是一组可移植 Skill 包，而不是绑定某个前端 Demo 或单一平台的应用。

```text
教师
-> Harness
-> research-proposal-coach Skill 包
-> 模型
-> 工具适配层
-> 学校材料 / 文献检索 / 文档平台 / 过程日志
-> 阶段产物与申报书结构化内容
```

设计原则：

1. Skill 内容优先使用 Markdown 规则、模板和示例，方便非技术 owner 维护。
2. Harness 只作为运行环境，Skill 的核心流程、质量规则和输出契约不写死在某个平台里。
3. 工具能力通过适配层接入，避免把飞书、Trae、豆包、Codex、Claude 等平台能力直接写进核心规则。
4. 客户可维护内容和工程适配代码分离。客户侧可以维护 Markdown，技术侧维护工具和集成。

### `SKILL.md`

定义入口指令、适用场景、禁止事项、运行顺序和工具调用边界。它不应堆满全部规则，而应引用 `rules/`、`modules/`、`templates/` 中的文件，让后续维护更清楚。

### `rules/`

存放稳定业务契约：

- `stage-contract.md`：8 个业务阶段、内部状态、通过条件、回退条件。
- `quality-rubric.md`：A/B/C 判定和模块级质量检查。
- `source-policy.md`：`user_confirmed`、`ai_suggestion`、`material_verified`、`retrieved_evidence`、`missing` 等来源状态。
- `guidance-principles.md`：如何像导师/学伴一样追问、解释、鼓励老师补充输入。
- `reviewer-standards.md`：学校科研处、专家、优秀案例沉淀出的好课题标准。

### `modules/`

每个模块都采用同一套循环：

```text
输入识别
-> 草稿生成
-> 原则解释
-> 关键追问
-> 用户确认或修订
-> 质量检查
-> 学习反馈
```

模块之间允许回退。例如在申报书映射阶段发现题目不贴合前文，应回退到课题方向或研究问题模块，而不是只在最终文本上做润色。

### `templates/`

模板用于约束输出结构，必须保留来源状态、缺口和人工确认点。文献综述需要同时支持两种长度：

- 长文档：帮助老师理解研究现状和案例，可作为额外学习产物。
- 申报书字段版：把长文档压缩成符合申报书字数和结构要求的短段落。

### `maintenance/`

让客户或运营 owner 可以低门槛维护：

- 新增或更新学校指南。
- 补充优秀案例和常见退回意见。
- 记录每次规则修改的原因。
- 标注典型失败案例，供后续评测使用。

## 核心模块设计

### 1. 教师画像模块

目标：知道老师是谁、做什么、过去做过什么、当前在哪些课程或岗位场景中有真实问题。

输入来源：

- 用户自述。
- 客户提供的教师信息表。
- 后续可选接入的人事、科研、教学系统。

关键字段：

- 院系、岗位、课程或工作职责。
- 过往科研、教改、课程建设、项目经历。
- 当前重点任务、专业群或学校战略关联。
- 可用资源、数据、班级、企业案例、合作条件。

首版规则：如果没有课程或工作场景，不进入选题推荐。

### 2. 选题发现模块

目标：从“AI+教育”“提升教学质量”等空泛意图中挖掘真实问题，并推荐 2-3 个可比较方向。

评价指针：

- 是否延续教师已有基础。
- 是否解决真实工作或教学问题。
- 是否贴合学校当前申报导向或专业建设重点。
- 是否有政策、文献、案例或数据支撑。
- 是否有可形成的非论文成果。
- 是否存在适度创新，而不是只套概念。

输出：

- 问题域摘要。
- 候选课题方向卡。
- 推荐排序理由。
- 需用户确认的问题。

### 3. 文献综述模块

目标：让老师知道“以前谁研究过、研究到哪里、还有什么值得做”，并生成可追溯的文献综述产物。

流程：

1. 基于课题方向生成检索 query。
2. 调用真实文献检索或客户允许的公开渠道。
3. 记录检索式、来源、时间、筛选条件和排除理由。
4. 对结果去重、重排序、聚类。
5. 生成研究现状、已有不足、案例启发和本课题切入点。
6. 追问老师是否了解本校或行业内更贴近的案例。
7. 生成长文档和申报书字段版。

硬性约束：

- 没有真实检索结果时，必须标记为 `missing` 或演示依据，不能编造引用。
- 文献综述不是一次性文本，而是后续研究问题、方法、创新点的依据。

### 4. 研究问题模块

目标：帮助老师写出有意义、可回答、可实施的关键问题。

判断原则：

- 问题要来自真实场景。
- 问题之间最多 3-5 个，关系应是并列互补或递进，不要堆砌。
- 每个问题要有对象、场景、现象、原因假设和可验证结果。
- 对小白老师要解释“问题”和“口号”“任务”“成果”的区别。

输出：

- 核心研究问题。
- 子问题列表。
- 问题关系说明。
- 不合格问题的修改建议。

### 5. 方法与成果模块

目标：把“想研究什么”转成“如何解决问题”和“形成什么成果”。

方法判断：

- 不能只写空泛理念。
- 必须形成一套工作体系、工具、流程、量表、任务包、案例库或实施方案。
- 每个方法要对应要解决的问题。
- 每个方法要能说明实施对象、周期、数据、评价方式。

成果判断：

- 论文可以有，但不能只有论文。
- 至少要有一个可复用、工具性、流程性或实践改进类成果。
- 成果要能支撑结题和学校实际使用。

输出：

- 问题-方法-成果对应表。
- 方法路径草案。
- 成果清单。
- 成果评分风险提示。

### 6. 创新点模块

目标：结合前文文献和案例，帮助老师提炼真实创新点。

创新点来源：

- 研究对象或场景的特殊性。
- 解决方案的体系化程度。
- 工具、流程、量表、任务包或案例库的可复用价值。
- 与已有研究或学校常见做法的差异。

约束：创新点必须能被前文材料支撑，不能凭空拔高。

### 7. 申报材料映射模块

目标：把长对话和模块产物压缩成符合学校申报书模板的结构化内容。

输入：

- 已确认的教师画像、课题方向、研究问题、文献综述、方法、成果、创新点。
- 学校申报书空白模板。
- 申报指南、字数要求、栏目说明、评审标准。

输出：

- 申报书字段映射稿。
- 字数压缩版内容。
- 缺口清单。
- 质量报告。

规则：申报书生成是最后一步的结构化压缩，不是前面思考过程的替代。

### 8. 学习反馈模块

目标：在每个模块结束后，给老师反馈其科研思维短板和下一步学习建议。

可记录维度：

- 是否能描述真实问题。
- 是否能提出可回答的研究问题。
- 是否理解文献综述的作用。
- 是否能区分方法、工具、成果和创新点。
- 是否能主动提供案例、数据和约束。

输出：

- 本轮对话短板。
- 建议阅读或补充材料。
- 下一轮可继续深化的问题。

## 数据与状态契约

### 来源状态

建议保留原有来源状态，并为真实检索增加更清晰的细分：

| 状态 | 含义 |
|---|---|
| `user_confirmed` | 用户明确表达或确认。 |
| `ai_suggestion` | 系统建议，等待用户采纳或修订。 |
| `material_verified` | 来自客户提供或可追溯真实材料。 |
| `retrieved_evidence` | 来自真实检索结果，需记录检索来源和时间。 |
| `demo_fixture` | 仅用于演示的占位数据。正式 Skill 默认不使用。 |
| `missing` | 当前缺失，必须进入待补充清单。 |

### Session 状态

每次立项引导应形成一个结构化 session：

```json
{
  "session_id": "string",
  "teacher_profile": {},
  "selected_topic": {},
  "research_questions": [],
  "evidence_records": [],
  "literature_review": {},
  "method_plan": {},
  "deliverables": [],
  "innovation_points": [],
  "proposal_mapping": {},
  "quality_grade": "A | B | C",
  "missing_items": [],
  "learning_feedback": [],
  "interaction_metrics": {}
}
```

### 过程日志

必须记录以下信息，服务后续评测 loop：

- 每个模块进入和退出时间。
- 当前模块输入是否由用户确认。
- Skill 生成过哪些草稿。
- 追问了哪些问题，用户是否回答。
- 哪些字段从 `ai_suggestion` 变成 `user_confirmed`。
- 哪些依据来自真实材料或检索。
- 质量等级为何变化。
- 用户是否直接跳过思考、要求一键生成。

## 工具与集成设计

首版优先把工具设计成可替换适配器：

| 工具能力 | 首版实现 | 后续扩展 |
|---|---|---|
| 教师画像读取 | 用户输入或导入结构化材料 | 人事、科研、教学系统接口或 MCP。 |
| 文献检索 | 公开检索渠道或客户指定数据库的人工/半自动接入 | 数据库 API、图书馆资源、专用检索工具。 |
| 学校材料读取 | 上传模板、指南、优秀案例 | 飞书云文档、知识库、Drive、内部资料库。 |
| 文档生成 | Markdown 结构化输出 | 飞书文档、DOCX、表单字段自动填充。 |
| 日志记录 | 本地 JSON/Markdown 过程记录 | 数据库、观测平台、评测数据集。 |
| 质量评测 | A/B/C 规则 + 人工复核 | LLM judge 辅助 + 人工抽检。 |

## 质量与评测

### 运行时质量门槛

继续沿用 C -> B -> A 的固定顺序：

- C：核心问题未建立，继续追问，不生成申报材料。
- B：核心思考基本成立，但真实材料、文献、模板或方法成果仍有缺口，只生成阶段性材料。
- A：核心字段确认，真实材料齐备，方法成果可执行，可生成申报书结构化内容草稿，但仍需人工和专家审核。

### 模块级检查

除总等级外，每个模块都应输出本模块检查结果：

- `pass`：可以进入下一模块。
- `needs_revision`：建议继续追问或修订。
- `blocked`：缺少关键材料或用户事实，不能继续。

### 评测样例

首批评测集至少包含：

1. 空泛输入：“我想做 AI+教育。”
2. 小白老师有真实课程问题，但没有研究问题。
3. 文献检索结果缺失时请求生成综述。
4. 只有论文成果，没有工具性成果。
5. 直播电商 B 级样例。
6. 真实模板、真实指南、真实文献齐备的 A 级样例。
7. 用户中途修改课题方向。
8. 用户要求“一键生成，不要问我”。

## 开发阶段计划

### P0：整理开发资产

- 新增 0820 会议总结。
- 归档一次性 demo 客户材料。
- 建立 Skill 包目录结构。
- 从 `05-stage-rule-blueprint.md`、`03-proposal-quality-rubric.md` 和本方案抽出首版 `stage-contract` 与 `quality-rubric`。

验收标准：开发者只读 Skill 包和本方案，就能理解首版目标、状态、输出和禁止事项。

### P1：无工具 Skill 原型

- 实现纯对话流程。
- 使用 Markdown 模板生成课题方案卡、研究问题、方法成果表、文献综述占位、申报字段映射。
- 固定来源状态和 A/B/C 输出。
- 记录 session 状态和过程日志。

验收标准：输入直播电商样例，能稳定得到 B 级阶段性材料；输入空泛需求，稳定判 C 并追问。

### P2：真实材料与检索接入

- 接入学校申报模板、指南、优秀案例和评审标准。
- 建立文献检索记录格式。
- 将 `demo_fixture` 替换为 `material_verified` 或 `retrieved_evidence`。
- 支持长文献综述与申报书字段版综述的双输出。

验收标准：真实材料齐备时可进入 A 级，但输出仍声明需要人工和专家审核。

### P3：试点与评测 loop

- 找 1-3 位试点老师跑完整流程。
- 人工复核每个模块的失败点和追问质量。
- 维护 `maintenance/update-log.md` 和评测案例。
- 根据客户反馈优化 Markdown 规则和模板。

验收标准：能解释每一次生成结果为什么好或不好，能定位失败发生在哪个模块。

## 开发验收清单

首版完成时必须满足：

1. Skill 明确定位为科研立项导师/学伴，不是代写工具。
2. 每个模块都有输入、输出、通过条件、回退条件和学习反馈。
3. C 级绝不生成申报材料。
4. B 级只生成阶段性材料，不生成正式申报书草稿。
5. A 级也只生成结构化内容草稿，并提示人工审核。
6. 文献、政策、模板、案例均保留来源状态。
7. 申报书内容能追溯到用户确认、真实材料或检索依据。
8. 客户可维护内容主要落在 Markdown 文件中。
9. 过程日志足够支持人工评测和后续迭代。
10. Skill 包不绑定单一 harness。

## 主要风险

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 客户真实材料迟迟不到位 | 无法进入 A 级真实申报书结构化内容 | 首版保持 B 级，清晰输出待补充清单。 |
| 文献检索渠道不稳定 | 综述真实性风险 | 先记录检索过程和来源，不足时降级为 `missing`。 |
| 追问过多影响体验 | 小白老师放弃使用 | 每个模块允许“快速版”和“深聊版”，但快速版要标记风险。 |
| Skill 被当成代写工具 | 产品价值偏离，材料质量下降 | 在入口、质量规则和输出中持续强调引导、确认和人工审核。 |
| 平台变化导致迁移 | 运行环境不稳定 | 核心规则 Markdown 化，工具接入适配层化。 |
| 自动优化预期过高 | 客户期待不可控 | 明确当前只做日志和人工评测 loop，不承诺全自动自学习。 |

## 开发启动结论

基于 0820 沟通，可以进入 Skill 开发阶段。开发重心不是复刻 demo，而是沉淀一个可移植、可维护、可评测的科研立项教练 Skill 包。旧 8 阶段流程仍是骨架，客户最新反馈要求我们在骨架之上补足“引导循环、学习反馈、过程日志、规则维护入口和评测 loop”。
