# 客户确认清单

## 用途

第一次 Demo 会议结束时，用这份清单记录客户确认项、修改意见、责任人和截止时间。目标是让客户明确确认流程、产物、质量规则和下一阶段材料责任。

## 会议基本信息

| 项目 | 内容 |
|---|---|
| 会议时间 | 待填写 |
| 参会人 | 待填写 |
| 演示版本 | 流程验证 Demo |
| 演示案例 | 从“AI+教育”收敛到直播电商实训教学改革课题 |

## 五组核心决策

| 决策组 | 需要确认的结论 | 客户修改意见 | 责任人 | 截止时间 |
|---|---|---|---|---|
| 定位与范围 | 是否认可“科研立项引导助手，而非简单代写工具”；首版是否只聚焦“小白老师不知道申报什么课题” |  |  |  |
| 流程与确认点 | 是否认可 8 阶段流程、追问顺序，以及课题方向、研究问题、依据、方法成果、字段映射等人工确认点 |  |  |  |
| 阶段产物 | 是否认可课题方案卡、申报书字段映射稿、待补充清单和质量结果作为本阶段产物 |  |  |  |
| 质量规则 | 是否认可 C/B/A 判定方式；哪些规则需要科研处或专家补充 |  |  |  |
| 资料与下一步 | 谁在第二版真实材料 Demo 前提供模板、指南、优秀案例、评审标准和脱敏要求 |  |  |  |

## 附录：详细问题池

- 从空泛输入开始纠偏的演示方式是否符合科研处期待？
- 网络营销与直播电商案例是否贴合学校专业特色？
- 对小白老师来说，教师画像和工作问题追问是否过多或过少？
- 课题方向推荐是否需要展示更多排序理由？
- 政策/指南影响选题判断的展示方式是否清楚？
- `demo_fixture`、`material_verified`、`missing` 等来源标记是否容易理解？
- B 级不生成正式申报书草稿的边界是否认可？
- 后续真实材料接入后，是否允许生成申报书结构化内容草稿？
