# 科研立项引导流程说明书

## 文档目的

这份文档用于向客户说明：我们如何把“帮助老师完成科研立项申请”的诉求拆成可验证、可确认、可继续建设的流程。

它是第一次流程验证 Demo 的客户附件，不是最终产品说明书。

## 本期建设目标

本期只聚焦科研立项申请，特别是“小白老师不知道申报什么课题”的场景。

目标不是让 AI 直接替老师写完材料，而是让系统像科研立项教练一样，通过有规则的对话帮助老师完成三件事：

1. 从真实工作中找到可研究问题。
2. 将问题转化为可申报课题方案。
3. 形成可进入申报书字段的结构化材料。

## 8 个业务阶段

| 阶段 | 解决什么问题 | 系统做什么 | 阶段产物 | 人工确认点 |
|---|---|---|---|---|
| 1. 教师画像采集 | 不知道老师是谁、做什么，就无法推荐课题 | 了解院系、岗位、课程、重点工作和可用资源 | 教师画像摘要 | 老师确认画像是否准确 |
| 2. 空泛意图纠偏 | 老师常从“AI+教育”“提升质量”等宽泛想法开始 | 不直接生成，追问具体课程、学生、环节、数据 | 收敛后的问题域 | 老师确认真实关注点 |
| 3. 工作问题挖掘 | 日常困扰还不是研究问题 | 追问痛点、对象、频率、影响和已有尝试 | 候选工作问题 | 老师选择最真实的问题 |
| 4. 课题方向推荐与确认 | 老师不知道哪个方向适合申报 | 推荐 2-3 个方向，说明理由、成果和风险 | 课题方向候选卡 | 老师选择方向 |
| 5. 研究问题澄清 | 课题名称不等于研究问题 | 帮老师把对象、场景、问题、方法、评价方式说清楚 | 研究问题草案 | 老师确认研究问题 |
| 6. 文献与政策支撑 | 课题需要说明为什么值得做 | 引入申报指南、政策、文献或优秀案例，并标明来源 | 依据说明 | 客户确认真实材料来源 |
| 7. 方法与成果设计 | 课题不能只有想法，要能实施和结题 | 设计方法路径、数据来源、实施计划和成果形式 | 方法路径和成果清单 | 老师确认资源和成果 |
| 8. 申报材料生成与质检 | 把思考转化为申报书准备材料 | 生成方案卡、字段映射稿、待补充清单和质量结果 | 阶段性材料包 | 客户确认质量规则和缺口 |

## 来源状态说明

每个关键结论都要显示来源，避免把系统建议或演示数据当成事实：

| 标记 | 含义 |
|---|---|
| `user_confirmed` | 老师明确说过或确认过 |
| `ai_suggestion` | 系统建议，仍需采纳或修改 |
| `material_verified` | 来自可追溯真实材料 |
| `demo_fixture` | 演示占位数据，不是真实依据 |
| `missing` | 当前缺失，需要客户补充 |

## 本次 Demo 的四项阶段产物

### 1. 课题方案卡

用于一页看清课题是否成立，包括问题、对象、方法、成果、依据、风险和待补充信息。

### 2. 申报书字段映射稿

把已确认内容放入通用申报书栏目，同时标记哪些字段还缺真实模板、指南或专家确认。

### 3. 待补充清单

列出下一版真实材料 Demo 前需要客户提供的模板、指南、优秀案例和评审标准。

### 4. 质量结果

用 A/B/C 告诉客户当前能生成什么、不能生成什么。

| 等级 | 含义 |
|---|---|
| C | 继续追问，不生成申报材料 |
| B | 可生成方案卡、字段映射稿、待补充清单和质量结果 |
| A | 可额外生成申报书结构化内容草稿，但仍需人工和专家审核 |

当前直播电商 Demo 因为指南是演示数据、模板仍缺失，稳定判为 B。

## 正式交付形态

第一次客户沟通使用独立网页让流程更直观。正式版本不把网页作为最终运行时，而是在成熟 Harness 中运行科研立项 Skill：

```text
教师
-> 成熟 Harness
-> 科研立项 Skill
-> 模型 / 工具 / 学校材料
-> 课题方案卡 / 字段映射稿 / 申报书结构化内容
```

客户本轮确认的是业务流程、判断规则和产物结构。确认后的业务规则将进入后续 Skill 建设。

## 本期成功标准

第一次 Demo 成功，不以生成一份完整正式申报书为标准，而以客户确认以下事项为标准：

1. 定位是否正确：科研立项引导助手，而非简单代写工具。
2. 首版场景是否正确：小白老师不知道申报什么课题。
3. 追问顺序和人工确认点是否符合真实申报过程。
4. 四项阶段产物是否适合客户校准。
5. 质量规则是否需要科研处或专家补充。
6. 第二版真实材料 Demo 前的资料责任是否明确。
